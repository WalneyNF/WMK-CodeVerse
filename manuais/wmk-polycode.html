1. O que é WMK PolyCode?

WMK PolyCode é o nome proposto para uma arquitetura e metodologia de integração de sistemas existentes com novas linguagens de programação, runtimes, APIs, protocolos de ferramentas como MCP e provedores de inteligência artificial.

Seu princípio é analisar os pontos de extensão legítimos de uma aplicação, identificar as interfaces estáveis disponíveis e desenvolver adaptadores que conectem novas capacidades sem reconstruir o núcleo inteiro.

Precisão técnica: este documento descreve uma visão arquitetural em desenvolvimento. Não existe, neste momento, um SDK universal WMK PolyCode validado em diferentes aplicações. O primeiro laboratório é o WMK CodeVerse, baseado no Godot.

2. Como nasceu a ideia?

O trabalho começou com um objetivo prático: incorporar outras linguagens de programação à Godot. O estudo do mecanismo de registro do GDScript, das APIs do motor C++ e das possibilidades de extensões revelou três necessidades diferentes: executar outras linguagens, acessar objetos do motor e integrar ferramentas externas.

Daí surgiu uma proposta mais ampla: registrar o conhecimento de integração em uma camada documentada, testável e potencialmente reutilizável em outros softwares. O foco inclui o público brasileiro, com Portugol como linguagem educacional de destaque.

Linguagens

Interpretação, compilação, transpilação e bindings: cada linguagem pode exigir um mecanismo diferente.

Ferramentas e MCP

Descoberta e chamada de ferramentas por agentes, com permissões, limites e auditoria; MCP não é um runtime de linguagem.

Provedores de IA

Cadastro, seleção de modelos, credenciais seguras e interfaces comuns; disponibilidade e custos dependem do provedor.

Adaptadores

Um adaptador específico para cada aplicação: as APIs do Godot não são automaticamente iguais às do Blender ou de outro software.

5. Componentes propostos do futuro SDK

  1. Host Adapter: identifica versão, APIs, permissões e ciclo de vida do software hospedeiro.
  2. Language Adapter: controla runtime, carregamento de scripts, interoperabilidade e conversão de tipos.
  3. AI Provider Registry: organiza provedores, modelos e configuração de endpoints; mantém segredos fora dos arquivos de projeto.
  4. MCP Gateway: registra ferramentas permitidas e suas políticas de execução.
  5. Capability Registry: declara ações acessíveis ao usuário e aos agentes; alterações exigem confirmação.
  6. Test Harness: executa demonstrações reproduzíveis e verifica comportamento, falhas e compatibilidade.

Exemplo hipotético de contrato

{
  "adaptador": "godot",
  "versao_api": "experimental-0.1",
  "linguagem": "portugol",
  "modo": "transpilacao",
  "destino": "gdscript",

  "modificacao_de_projeto": "somente_com_aprovacao"
}

Esse JSON é ilustrativo e não corresponde a uma API já implementada.

6. Segurança, licenciamento e limitações

  • Dar preferência a código-fonte disponível, extensões documentadas e APIs autorizadas; não presumir acesso irrestrito a qualquer aplicativo.
  • Isolar runtimes e restringir acesso a disco, rede e execução de processos quando possível.
  • Exigir consentimento para ações de IA que escrevam, executem ou removam arquivos; registrar as operações.
  • Guardar chaves de IA fora dos repositórios e arquivos de exportação de jogos.
  • Preservar licenças, marcas e avisos de terceiros, incluindo os da Godot e das bibliotecas integradas.
  • Não confundir protótipos de código com funcionalidades validadas ou com um produto final estável.

7. Roteiro de validação

  1. Fase 1 — Documentação: visão, contratos, arquitetura e inventário dos pontos de extensão Godot.
  2. Fase 2 — Demonstração: Portugol → GDScript → cena 2D executada automaticamente no Godot.
  3. Fase 3 — Linguagens: uma cena e testes automatizados para cada runtime ou binding incorporado.
  4. Fase 4 — IA/MCP: interface de cadastro, permissões e assistência prática ao desenvolvimento.
  5. Fase 5 — SDK: extrair contratos estáveis e demonstrar ao menos dois adaptadores de aplicações distintas.
  6. Fase 6 — Distribuição: Windows ZIP experimental, instruções reproduzíveis, matriz de compatibilidade e releases.
